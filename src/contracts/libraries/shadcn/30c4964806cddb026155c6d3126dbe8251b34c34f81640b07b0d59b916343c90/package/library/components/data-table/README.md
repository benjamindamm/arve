Describe the official native Table + TanStack feature recipe, keeping sorting, filtering, pagination, visibility and row selection distinct.

DataTable is the official Table+TanStack guide recipe, not an invented exported widget root. Caller semantic data-part marks only recipe-owned toolbar, filter, selection, sort action, empty/error/count and page navigation. Complete Table CSS explicitly owns all native table row/cell/head/caption geometry; Button/Input CSS own those actual source controls. The recipe retains native compact 16px selection affordance and uses bounded readable spacing/filter width decisions instead of558px native specimen width. Actual selected row data-state and native checkbox are independent from sorting/filtering/paging/visibility states. Stable getRowId binds checkbox names and state to records; current aria-sort belongs to real scoped header. Empty colSpan follows visible column count. Error is caller feedback and does not erase controlled feature state. DashboardDataTableBlock is explicitly a separate frozen application composition, not rendered extra anatomy. Native table semantics stay native; no fictitious ARIA grid navigation, record schema or backend lifecycle.

There is no universal upstream DataTable root primitive. The official pinned Base UI data-table guide defines a caller DataTable<TData>({columns,data}) composition using Table and TanStack Table v9. This reference pins @tanstack/react-table/table-core9.3.1, matching that documented major; v8 get*RowModel APIs are not silently substituted. tableFeatures opts into columnFilteringFeature/columnVisibilityFeature/rowPaginationFeature/rowSelectionFeature/rowSortingFeature, registers createFilteredRowModel/createPaginatedRowModel/createSortedRowModel and includesString/text functions. Core row model is automatic. useTable owns derived feature models; separate state/onSortingChange/onColumnFiltersChange/onColumnVisibilityChange/onRowSelectionChange/onPaginationChange can be caller controlled, and each callback receives a value or updater function—not Base UI eventDetails. columns supplies real accessor/display and header/cell renderers; table.FlexRender renders actual definitions. Sorting only applies where enabled and affects row order, not selected IDs. Filters affect the filtered model; pagination shows that model, with native boundary-disabled Previous/Next controls; source default page size10 is explicitly overridden to2 in this reference. Visibility changes cells and empty-state colSpan, not row data. Stable getRowId is deliberately set to payment.id so sorting/filtering/paging cannot relabel a selected row; default index identity is not assumed safe for externally reordered data. Row selection stores ID booleans independently, so hidden/filtered selected rows may remain selected. Select-all-page and select-all-filtered are distinct source APIs, never conflated. Table is a native table, not an interactive ARIA grid or spreadsheet; no roving cell keyboard/editing behavior is promised. Upstream docs basic example does not add every accessible context: reference supplies real caption, scope=col, aria-sort on current sortable email header, named row checkboxes, visible filter label, pagination landmark and polite matching count. No results is a real row with current visible-column colSpan. Loading/fetch/error/retry are explicit caller concerns; simulated error and durable feedback here are local and do not imply server fetching. The separately frozen dashboard-01 DataTable({data}) block uses its own schema, tabs, drag/reorder, chart/detail and actions; it is a supplementary concrete block, not an additional generic widget API or compulsory feature of every table recipe.

Native Tab/Enter/Space reach actual filter/header buttons/row checkboxes/page buttons; text editing remains native. Sorting changes aria-sort and row order without moving focus to a row. Disabled boundary page buttons cannot activate. Row selection is native checkbox state and does not turn tr into a command. Hidden columns remove their controls from the tree; filtered/empty/error feedback remains readable. Escape and arrow keys have no invented table selection/activation meaning; composed menus/dialogs retain their own completed contracts.
